먼저 FocusOn API 명세서를 수정했다. 분석에서 제외할 도메인을 조회하고 전체 교체할 수 있는 API를 추가했고, 학습 정리 응답에서는 사용하지 않기로 한 reviewQuestions를 제거했다. 또한 세션, 분석, 개입 응답에 정책 버전을 나타내는 policyVersion을 반영했다.

ERD도 API 명세에 맞춰 수정했다. 분석 제외 도메인을 저장하는 analysis_excluded_domains 테이블을 추가했고, 세션·분석·개입 테이블에도 정책 버전 필드를 추가했다. 학습 정리 JSON 구조와 관련 제약 조건, 인덱스, API와 데이터베이스 간 매핑도 함께 정리했다.

AI 분석 계약도 구체적으로 다시 정했다. GENTLE은 120초, NORMAL은 10분 안에 30초 이상 이탈이 2회 발생했을 때, ACTIVE는 30초를 기준으로 하도록 했다. UNCERTAIN 상태는 30초 이하일 때 보류하고, 초과하면 구간을 종료하도록 정했다. RELATED 상태가 15초 이상 지속되면 이탈 구간을 초기화하도록 했고, 세션과 개입 유형별로 5분 cooldown을 적용하기로 했다. 세션 시작 시에는 focus-intervention-v1 정책을 고정해서 사용하도록 정리했다.

Heartbeat 정책도 다시 확인했다. 10초마다 확인하고, 60초 동안 신호가 없으면 후보 상태로 판단하며, 3분 동안 복구되지 않으면 ABANDONED로 전환하도록 했다. 마지막으로 확인된 누적 시간만 반영하고, 자동 종료된 세션은 다시 복구하지 않는 규칙도 정리했다.

마지막으로 API 명세서, ERD, AI 분석 계약, 세션 상태 전이 정책을 서로 비교하면서 정합성 검사를 진행했다. 그리고 FocusOn API 명세서를 유일한 정본으로 정하고, 문서 인덱스가 정본 DB를 직접 가리키도록 수정했다. 기존 API 명세서는 ARCHIVED / 이전·보조 자료로 분리해서 혼동이 없도록 했다.

## 일주일 동안 겪었던 힘든 점, 극복했다면 해결 방법

이번주에는 문서 하나만 수정하는 것이 아니라 API 명세서, ERD, AI 분석 계약, 세션 상태 정책을 모두 서로 맞춰야 해서 어려움이 있었다. 한 문서에서는 맞는 내용이 다른 문서에서는 다르게 적혀 있는 경우도 있었고, 정책 버전이나 세션 상태처럼 여러 문서에 동시에 반영해야 하는 내용도 많았다.

특히 AI 분석 상태별 기준과 Heartbeat 상태 전이를 구체적인 시간 기준으로 정하는 과정이 오래 걸렸다. 단순히 상태 이름만 정하는 것이 아니라 실제 상황에서 언제 후보로 판단하고, 언제 종료하며, 언제 개입을 발생시킬지까지 정해야 했기 때문이다.

이 문제를 해결하기 위해 문서별로 따로 수정하지 않고, API 명세서와 ERD를 기준으로 AI 분석 계약과 세션 정책을 하나씩 대조했다. 서로 다른 부분은 회의를 통해 기준을 다시 정하고, 최종적으로 모든 문서에서 같은 용어와 시간 기준을 사용하도록 정리했다.

## 내가 잘한 것과 더 잘할 수 있었는데 아쉬웠던 점

이번주에 잘한 점은 단순히 API를 추가하거나 ERD를 수정하는 데 그치지 않고, 관련된 정책들을 함께 확인하면서 전체 구조의 정합성을 맞춘 것이다. 분석 제외 도메인, 정책 버전, 세션 상태, 개입 cooldown처럼 여러 기능에 영향을 주는 내용을 문서마다 빠짐없이 반영하려고 했다.

또한 API 명세서를 유일한 정본으로 정하고 기존 문서를 보조 자료로 분리한 것도 잘한 점이라고 생각한다. 개발자마다 서로 다른 문서를 참고해서 구현하는 문제를 줄일 수 있기 때문이다.

아쉬운 점은 처음부터 API, ERD, AI 분석 계약을 함께 연결해서 설계했으면 수정하는 시간이 더 줄었을 것 같다는 점이다. 특히 정책 버전이나 학습 정리 JSON 구조처럼 나중에 여러 문서를 동시에 수정해야 하는 항목은 초기에 더 명확하게 정의했어야 했다.

## 다음주까지 해올 것

FocusOn API 명세서와 ERD를 최종 확정하고, 수정된 정책을 백엔드 server 문서에도 반영할 것이다.

또한 AI 분석 계약과 Heartbeat 상태 전이 정책을 개발자가 바로 참고할 수 있도록 정리하고, 세션·분석·개입 기능의 구현 기준을 구체화할 것이다.

문서 최종 검토를 마친 뒤에는 정해진 API와 데이터베이스 구조를 바탕으로 백엔드 개발을 시작하고, 구현 중 새롭게 발견되는 예외상황이나 정책은 정본 문서에 계속 반영할 예정이다.
