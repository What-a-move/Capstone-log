일주일 동안 아이디어에만 집중한거 같다. 그늘로라는 앱이 있는데 그 앱이 건물의 높이와 해의 각도를 계산해 그늘이 있는것들을 알려주는 앱있는데 그런 형식의 프로젝트를 하고 싶었다.

그래서 사회적 문제를 해결하고 사람들이 쉽게 접근하지 못해 생각하지 않는 아이디어를 생각해 보자라고 생각했다.
그래서 생각해서 나온게 소리눈이라는 아이디어를 생각했다.
소리눈은 시각 장애인분들을 위한 서비스로 자동차 경적이나 초인종, 벨 소리 등의 주파수를 모델에 학습시켜 휴대폰에 진동이 오도록 하는 서비스 이다.
나는 소리눈이라는 프로젝트가 정말 마음에 들었다 왜냐하면 주파수라는 개념에 쉽게 접근하거나 생각하지 못했고 이러한 프로젝트를 한다면 내 지식과 흔치않는 경험이 될거 같아서 이다.
하지만 소리눈이라는 아이디어가 이미 시장에 널리 펴진 아이디어들 이었다.
나는 그래도 차이점을 주면 되겠지라고 생각해서 그냥 한국전용으로 모델을 학습시키면 차별점이 있을까 했다.
하지만 안드로이드나 우리 아이디어와 거진 비슷한 프로젝트가 많아 이 프로젝트는 하지 않기로 헀다.
근데 이 아이디어가 무산되었다 해도 얻은것은 있었다.
제일 먼저 아이디어를 범위를 확장한거 같다.
우리는 평소에 그냥 웹서비스, 그저 사회적 문제만 해결하는 아이디어만 짯다.
하지만 이 아이디어를 보고나니 생각의 범위가 늘어 다른 생각들도 많이 한거 같다.
예를 들어 기울기나 진동과 같은 새로운 생각들도 하게 되었다.
그래서 비록 아이디어는 무산 되었지만 아직 끝난것이 아니라서 이러한 방식으로 여러가지의 신선한 아이디어를 얻을수있다

이번주는 저번에 만든 최상위 기획서를 바탕으로 백엔드 쪽 문서들을 다시 정리하는 걸 했다.
지금까지는 API 응답 형식이나 에러 코드 같은게 그냥 대충 정해져 있었는데, 이대로 개발 들어가면 나중에 사람마다 다르게 만들어서 문제 생길것 같아서 다시 하나하나 정리했다.
성공했을 때 응답 형식이랑 실패했을 때 응답 형식을 통일하고, 최상위에 code 필드를 따로 안 넣기로 한것도 다시 확인했다. 그리고 에러코드 Enum도 뭉뚱그려서 하나로 퉁치지 않고, 예외처리를 확실하게 하려고 상황별로 세부화시켜서 나눠놨다. 나중에 기능 만들면서 더 필요한 케이스 생기면 여기다 계속 추가하기로 했다.
백엔드 담당자가 작업할 때마다 확인해야되는 규칙들도 Rule ID 붙여서 따로 정리했다. 응답 형식, 에러코드, Controller·Service·Repository 나누는거, 인증 헤더 형식, 로그에 민감한 정보 남기면 안되는거 이렇게 다섯 개로 나눴다.
제일 오래 걸린건 아직 안 정해진 것들 결정 기록에 남기는 거였다. 원래 있던 것들 말고 이번에 새로 찾은것도 세 개 추가했다. 하나는 연결 코드를 두 기기가 거의 동시에 쓰면 둘 다 통과돼버릴 수도 있는 문제, 하나는 세션 연장 버튼 두번 누르면 시간이 두번 늘어날 수도 있는 문제, 하나는 에러 응답에 들어가는 fieldErrors랑 requestId 형식이 아예 안 정해져 있는 문제였다. 이거 안 정하고 각자 만들면 나중에 다 다시 맞춰야 돼서 미리 적어놨다.
그리고 로그인, 기기연결, 학습세션, 목표, 분석, 리포트 이렇게 나눠서 예외상황도 다시 쭉 훑어봤다. 기획서에 이미 있는것도 있었고, 없는데 생각해보니까 필요한것도 꽤 있었다.
